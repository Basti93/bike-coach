# Bike Coach: KI-Coach (Stufe 2) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ein Coach erstellt pro Person die nächste Einheit und den Langzeitplan, passt beides an echte Fahrten an und begründet seine Änderungen, ohne dass eine Fahrt je von ihm abhängt.

**Architecture:** Der Coach läuft als eigener `utilityProcess` neben dem Fahrdienst und liest dessen Fahrten nur lesend. Er ruft nach einer Fahrt `claude -p` auf, prüft die Antwort mit festen Leitplanken und speichert die fertige nächste Einheit. Fällt Claude aus, liefert ein Regelwerk die Einheit.

**Tech Stack:** TypeScript, Vitest, `zod`, `ws`, React; `claude -p` über `child_process.spawn`.

**Spec:** `docs/superpowers/specs/2026-10-31-bike-coach-design.md`, Abschnitte 5 und 8.

## Global Constraints

- Keine Fahrt hängt am Coach. Absturz, Hänger oder Limit des Coachs ändern nichts am Start oder Ablauf einer Fahrt.
- Der Coach schreibt nie in `rides/<rideId>/`.
- `claude -p` wird unverändert genutzt und **ohne** `--bare`, weil `--bare` den Abo-Login nicht liest. Keine Coach-Werkzeuge: `--tools ''`.
- Die KI bekommt Puls, FTP und Fahrtdaten, aber keine Profilnamen.
- Jede KI-Einheit läuft vor der Annahme durch die Leitplanken im Code. Ungültiges wird verworfen und durch die Regel-Einheit ersetzt.
- Kein Wochenkalender. Verpasste Tage werden nie nachgeholt und nie als Versäumnis formuliert.
- Plan stimmt, wenn die Belastung langsam steigt, die FTP-Prognose ungefähr eintrifft und die meisten Einheiten „genau richtig“ sind.
- Commit-Nachrichten enden mit `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>` und `Claude-Session: https://claude.ai/code/session_013UaCPTKUHvZz5EkeAhjh96`.
- Oberflächentexte auf Deutsch mit korrekten Umlauten.

## Review Focus

1. App wird aus dem Finder gestartet und `claude` liegt nicht im PATH: Der Pfad wird über die Login-Shell gefunden; klappt das nicht, läuft das Regelwerk mit sichtbarem Hinweis. (Task 3)
2. Plan-Limit erschöpft oder `claude` hängt: Abbruch nach Zeitlimit, gespeicherte oder Regel-Einheit steht bereit, späterer Nachholversuch. (Task 3, Task 5)
3. Claude liefert Unsinn, oder ein Freitext enthält Anweisungen wie „ignoriere die Regeln“: Die Leitplanken lehnen eine überzogene Einheit trotzdem ab. (Task 2, Task 4)
4. Beide fahren abwechselnd: Fahrten, Plan und Hinweise einer Person beeinflussen die der anderen nie. (Task 4)
5. Erste Fahrt ohne Historie, lange Pause oder defekte Zustandsdatei: Es gibt immer eine sanfte, gültige Einheit, und die App startet weiter. (Task 2, Task 4)

  - `loadState(dir, profileId, initialFtpW): CoachState`, bei defekter Datei: Sicherung als `.broken`, neuer Zustand. `saveState(dir, state): void`, atomar.
  - `class Coach { constructor(deps: { ridesDir; coachDir; ask: (input: { prompt: string; systemPrompt: string; schema: object }) => Promise<unknown>; nowMs: () => number }); scanRides(profiles: Profile[]): void; refresh(profileId: string): Promise<void>; feedback(profileId, rideId, rating): void; note(profileId, text): void; adjustNext(profileId, how): void; state(profileId): CoachState }`

KI-Antwort (`zod` und JSON-Schema aus derselben Quelle):
`{ phase: { name, weeksLeft, goal }, ftpForecast: [{ weeksAhead, ftpW }], session: Session, reason: string, change: string, noteReply?: string, ftpChangeW?: number }`

Regeln:
- `refresh` ist je Profil nie gleichzeitig aktiv. Läuft ein Aufruf, wird nur `dirty` gesetzt.
- Rampentest: FTP wird nur aus `ftpFromRamp` übernommen. `ftpChangeW` der KI wird auf ±5 % begrenzt und höchstens einmal in 14 Tagen übernommen.
- Bei `hitCeiling` wird der Rampentest mit der neuen FTP erneut vorgeschlagen.
- Wurde noch kein Rampentest gefahren, ist `next` der Rampentest.
- Prompt enthält Zusammenfassungen der letzten 28 Tage, Belastung, Plan, Bewertungen und Hinweise. Freitext steht in einem als reine Daten markierten Block.
